# 운영 차량 연동 검사

iPhone 시뮬레이터의 앱과 공식 Pleos 에뮬레이터의 차량 앱을 같은 운영 픽업에 연결하는 검사다. 로컬 HTTP 응답을 바꾸는 기존 UI 검사와 구분한다.

## 환경

- iPhone 18 Pro 시뮬레이터 / iOS 27.0 / Xcode 27.2
- Pleos Connect 2.1 / Android 14 / 차량 앱 0.2.35-preview, versionCode 37
- API: `https://majung.cloud`
- 위치·ETA: 공식 에뮬레이터 내비 예제 경로

## 시나리오

| 검사 | 확인 내용 |
| --- | --- |
| `test10LiveVehicleRoundTrip` | 초대 참여, 실제 SDK ETA 표시, 메시지 전달, 앱 종료 후 같은 픽업 복귀, 같은 좌표 거절 후 다른 검색 결과로 제안, 차량 수신·철회, 준비 완료, 도착·완료, 처음 화면 복귀 |
| `test11LiveCancellationWhileTypingAndExpiredInvite` | 메시지 초안 입력 중 차량 취소 수신, 편집·준비 화면 제거, 앱 재실행 후 종료된 세션 미복구, 취소된 초대 재참여 차단 |

차량 계측은 준비 상태·메시지·장소 제안의 실제 수신을 확인하고 도착·완료 또는 취소 요청을 보낸다. 차량 버튼을 사람이 누르는 시연과는 구분한다. 취소·완료 뒤에는 차량의 공유 서비스 종료와 저장된 접근 정보 제거를 확인한다.

같은 위치 제안은 서버의 `SAME_PLACE` 거절을 유지한다. 앱은 위치가 같다는 이유와 지도 이동·다른 장소 검색 방법을 함께 안내한다. 로컬 UI 회귀에서도 같은 오류를 받은 뒤 설명 보존·검색 결과 재선택·재전송을 검사한다.

## 실행 조건

일반 CI는 운영 초대가 없으면 두 검사를 건너뛴다. 운영 검사를 실행하려면 새 시험 픽업과 비공개 `.xctestrun` 설정이 필요하다.

1. `xcodebuild build-for-testing`으로 앱과 UI 검사 빌드.
2. 차량 계측의 `publicBrowser=true`, `participantClient=iosSimulator` 지정. 진행 중인 다른 픽업이 있으면 검사 중단.
3. 차량 QR에서 얻은 새 참여 링크를 비공개 `.xctestrun`의 UI 테스트 러너 `EnvironmentVariables.MAJUNG_LIVE_INVITE`에 지정. 앱의 `MAJUNG_TEST_PORT`는 지정하지 않음.
4. 선택한 UI 검사 하나만 `test-without-building`으로 실행. 실제 iPhone에서는 실행하지 않음.
5. 완료·취소와 남은 시험 픽업을 확인한 뒤 비공개 설정 정리.

완료 검사의 차량 인수는 `participantMessage=ios-simulator-check`, `participantProposal=true`, `browserFinishMessage=ios-simulator-arrival-confirmed`다. 취소 검사는 `cancelAfterReady=true`를 사용한다.

초대 링크가 포함된 설정과 원본 실행 로그는 저장소 밖에서 관리한다. 공개 결과에는 초대 토큰·참여 토큰·원본 위치 로그를 넣지 않는다. 차량 검사의 정리는 해당 검사에서 만든 픽업에만 적용한다.

## 확인 범위

실제 카카오 인증, 물리 카메라 QR 촬영, 실물 iPhone, APNs 원격 푸시, 유니버설 링크와 실차 주행은 이 검사에 포함하지 않는다. 초대 참여는 가입 없는 탑승자 경로이며 카카오 로그인 검증으로 기록하지 않는다.


## 2026-11-14 운영 실행 결과

- 정상 경로: iOS 87.752초 / 차량 114.863초 통과
- 입력 중 취소·종료 세션 미복구·만료 링크 차단: iOS 49.693초 / 차량 59.908초 통과
- 첫 제안의 같은 좌표 거절은 서버 정책에 따른 동작으로 확인. 다른 검색 결과로 다시 제안한 회차 통과
- 취소 후 새 픽업 회차는 다른 작업의 APK 삭제·신규 설치로 차량 등록이 사라져 생성 전 중단. 취소로 인한 등록 손실 또는 재요청 통과로 기록하지 않음

두 운영 회차에서 만든 픽업은 완료·취소로 정리했다. 다음 운영 검사 전에는 차량 등록 상태와 동시 설치 작업 여부를 확인한다.

기존 로컬 회귀 32개 단위 검사·6개 UI 검사는 모두 통과했다. 운영 초대 미지정 상태의 2개 운영 검사는 의도적으로 건너뛰었다.

## 초대 입력 화면 경고 보완

초대 입력란에 포커스를 줄 때 키보드 전용 툴바를 구성하던 경로에서 `Invalid frame dimension` 경고를 재현했다. 툴바 안의 간격만 바꾼 비교 검사에서도 경고가 남았고, 키보드 닫기 버튼을 앱의 하단 안전 영역으로 옮긴 비교 검사에서는 경고가 발생하지 않았다. SwiftUI 내부 구현의 결함으로 단정하지 않는다.

로그인 전 초대 입력과 로그인 후 홈의 같은 툴바를 공통 하단 바로 변경했다. `test06GuestAndHomeInviteKeyboardRepeatedFocusDismissAndSubmit`에서 두 화면의 반복 포커스·닫기·초대 확인·참여를 검사한다. 이 검사 추가 뒤 UI 검사는 7개이며, 운영 전용 2개와 구분한다. 자세한 비교 결과는 [이슈 39](https://github.com/majung-team/majung-ios/issues/39)에 기록한다.


## 취소·완료 뒤 로컬 도착 알림 정리

운영 취소 검사에서 종료 화면 위에 직전의 ‘곧 도착’ 알림 배너가 남는 현상을 확인했다. 종료 상태에서 알림을 정리하는 경로가 없었다. 취소·완료·만료 시 해당 픽업의 예약·전달 알림을 제거하고, 차량 도착 시 이전 접근 알림을 제거한다. 알림을 끄거나 권한 거절을 확인한 경우에도 현재 추적 중인 알림을 정리한다.

알림 등록 응답보다 종료 이벤트가 먼저 도착해도 취소된 등록이 끝나는 즉시 다시 제거한다. iOS가 이미 표시 중인 시스템 배너는 알림 기록 제거만으로 즉시 닫히지 않을 수 있어, 앱 실행 중에는 화면의 도착 안내와 소리만 사용한다. 앱 밖의 시스템 알림은 유지한다. 단위 검사에서는 종료 상태·알림 끄기·도착 전환·등록 중 취소 경합을 확인한다. 추가 검사 3개를 포함한 단위 35개 통과. 네이티브 APNs 수신과 실물 iPhone 검증을 뜻하지 않는다.

브라우저에 접근할 수 없는 운영 재검사에서는 서버의 기존 내부 시험용 일회용 등록 코드를 이용해 별도 시험 차량을 등록했다. 운영 DB에 계정 연결을 직접 기록하거나 로그인 쿠키를 복사하지 않았다. 이 경로는 일반 운전자의 QR·카카오 최초 연결 검사와 구분한다. 실제 운영 서버 연동의 추가 결과는 [공통 검증 기록](https://github.com/majung-team/majung/blob/main/docs/rehearsal-2026-11-13.md)에서 확인한다.


## 실시간 현황의 정보 유효 시간

차량이 보낸 `validForMillis`에 맞춰 ActivityKit의 `staleDate`를 설정한다. 위젯은 `isStale`일 때 기존 ETA·도착 확정 표시 대신 ‘갱신 필요’와 앱 열기 안내를 보여준다. 명시적인 STALE·유효 시간 0 응답에서 이전 ETA를 재사용하지 않으며, 차량 정보가 없는 상태에서도 유효 시간이 끝난 이전 카운트다운은 재사용하지 않는다. 예상 도착 시각이 같아도 새 응답으로 유효 시간이 늘어나면 위젯 정보를 갱신한다.

앱이 백그라운드로 간 뒤의 갱신 유예는 최대 25초이며 OS가 더 일찍 끝낼 수 있다. 이후 서버의 취소·완료를 계속 받는 원격 갱신 기능은 아니다. 앱을 다시 열어 최신 상태를 확인해야 한다. 로컬 카운트다운 표시와 APNs 기반 원격 상태 갱신을 구분한다. [Apple의 staleDate·isStale 안내](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities)를 기준으로 한다.

다이나믹 아일랜드 터치 복귀 검사는 `app.activate()` 보조 동작을 제거하고 실제 전경 복귀를 확인한다. 새 유효 시간 회귀 2개를 포함한 단위 검사는 39개다.

`test07StaleLiveActivityShowsRefreshHintAndOpensPickup`는 정상 ETA 표시 뒤 STALE 응답으로 전환하고, 홈 화면 위젯의 ‘갱신 필요’ 표시·터치 복귀·픽업 완료 후 위젯 제거를 확인한다. 이 검사 추가 뒤 로컬 UI 검사는 8개다. 최초 시도는 차량 정보가 한 번도 들어오지 않은 상태에서 위젯을 찾다가 실패했으며, 정상 표시 중 정보가 오래되는 시나리오로 구성해 재검사했다. 초기 정보가 전혀 없는 상태의 위젯 생성 검증으로 기록하지 않는다.
